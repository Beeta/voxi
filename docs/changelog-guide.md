# CHANGELOG 怎么写

`CLAUDE.md` 的「版本与 CHANGELOG」写的是**什么时候动版本号**，这里写**条目怎么写**。

## 读者是未来的自己

voxi 的 CHANGELOG 不面向部署者（它没有 `.env`），也不面向新用户（那看 `README.md`）。
它面向半年后的你，以及替你改代码的 Claude。回答的是：

- 这个功能是哪个版本进来的？
- 当时为什么这么改？我踩过什么坑？
- 从旧版本升上来，我会遇到什么？

所以「做了什么」和「为什么」一样重要。提交信息里那几段推理（根因是什么、为什么不选
另一个方案）正是 CHANGELOG 要的东西，别在写条目时丢掉。

## 小节怎么分

| 小节 | 收什么 | 判断问题 |
| --- | --- | --- |
| 升级注意 | 换版本前必须知道的事 | 不看我这条，会不会踩坑？ |
| 新增 | 用户能指出来的新东西 | 我会不会想跟别人说「这版能 XX 了」？ |
| 变更 | 已有行为改了 | 以前是这样，现在不是了？ |
| 修复 | 之前是坏的，现在好了 | 它曾经不工作吗？ |
| 内部 | 用户感知不到 | 用户能看出来吗？看不出来就放这儿 |

**没有内容的小节不要留空标题。** 只有「内部」的版本不值得发版，继续攒。

几个容易判错的：

- **顺手修的 bug 跟新功能混在同一个提交里** → 分两处写。用户升级时关心的是「我以前
  遇到的问题解决了吗」，埋在新增条目里就找不到了。
- **性能优化** → 用户能感觉到（打开变快了）算「变更」，纯内部（少一次循环）算「内部」。
- **改默认值** → 算「变更」，而且大概率也要写进「升级注意」——老用户的设置不会跟着变，
  这是最容易让人以为「改了没用」的一类。
- **改存储格式 / 文件布局** → 一律写进「升级注意」，并说清旧数据还能不能用、要不要搬。

## 一条怎么写

写具体的东西，不写评价。名字、数字、路径能写就写。

| 别这么写 | 这么写 |
| --- | --- |
| 优化了设置页的交互 | 修复设置里的点击不生效：浅色/深色切不动，音频源开关也无效 |
| 调整了界面细节 | 播放器移到底部并压扁（按钮 46→32，时间字号 12→11），页签内容在它上方滚动 |
| 修复了一个崩溃问题 | 修复导入含空格文件名的音频后闪退：Go 1.22 的 `ServeMux` 把 pattern 里的空格当 method 分隔符，`HandleFunc` panic 终止了进程 |

不用「优化」「提升」「增强」「体验更好」这类词开头——它们不携带信息。修 bug 要写根因，
因为半年后你只会记得「当时有个坑」，不会记得坑长什么样。

## 格式模板

```markdown
## [未发布]

### 新增

- 新东西一句话说清，需要时补一句为什么。

## [X.Y.Z] - YYYY-MM-DD

### 升级注意

- 换版本前必须知道的事，写清不这么做会怎样。

### 新增

- ……

### 变更

- ……

### 修复

- 根因 + 修法。

### 内部

- 重构、测试、依赖、文档。一句带过即可。
```

## 未发布节的维护

- **同一个东西反复改只留一条。** 连着五个提交都在调同一个功能的间距，那是一条，不是五条
  ——改已有的那条，别新加。
- **条目可以随时改。** 未发布节不是承诺，发现写歪了就改。
- **发版时整节搬走。** 把 `## [未发布]` 改成 `## [X.Y.Z] - 日期`，在上面新起一个空的
  `## [未发布]`，然后按 `CLAUDE.md` 的表格决定版本号并打 tag。
